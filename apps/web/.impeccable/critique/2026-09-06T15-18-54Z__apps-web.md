## Priority Issues

**[P1 — CONFIRMED] The round-6 trend-chart fix over-corrected into a misleading chart.** `toTrendBarHeights` is min-max normalization: the series' minimum *always* renders at the 8px floor and the maximum *always* at 100%, with no baseline label. I verified the math directly — any nonzero variation, however small, stretches to fill the entire bar height. A 40%→46% move (6 points) now looks visually identical to a 10%→90% move (80 points): both render as "empty" to "full". Mobile still uses literal-percentage widths (unchanged from `toTrendBars`), so the same data draws a modest slope on a phone and a dramatic cliff on a laptop. **Fix:** pad the domain (e.g. `min − 10pp` to `max + 10pp`, floored at 0/ceilinged at 100) instead of exact min/max, and use the same domain logic on both breakpoints, or print the axis floor/ceiling under the chart.

**[P1 — CONFIRMED] The "demote Revogar consentimento" fix changed the button shape but not its color.** I measured it directly: computed `color` is `rgb(92, 107, 100)` — that's `--color-muted`, not the danger red the `text-danger` className was meant to apply. `variant="ghost"` already emits `text-muted` via `VARIANT_CLASS`, and my className addition lost the specificity tie (both are single-class utilities of equal specificity; Tailwind's generated stylesheet happens to order `.text-muted` after `.text-danger`, so `text-muted` wins regardless of prop order). The visible result is a plain grey word indistinguishable from the static paragraph above it — no color, no underline, no icon, no border. `enabled:hover:text-danger-strong` does work (higher specificity), but a phone user never sees a hover state. **Fix:** force the color to win (`!text-danger`) or use a variant that doesn't fight it, and add a non-color affordance (underline) so the control doesn't rely on a color override that's this fragile.

**[P2 — CONFIRMED] The collapsed chat shortcut's visible label isn't contained in its accessible name (WCAG 2.5.3).** `aria-label="Falar com uma pessoa real"` while the visible text reads "Falar com alguém" — I confirmed this in the source (`ChatActionTray.tsx:48,53`). These don't share the same phrase, so a voice-control user saying what they see won't match the accessible name. This is a regression from round 5's own fix (the previous visible text, "Pessoa real", was a substring of the aria-label and passed 2.5.3; the newer, warmer text broke it). **Fix:** either match the visible text to the aria-label, or make the aria-label match the shorter visible text — whichever framing the product wants to keep.

**[P2] The round-6 notification resend action has no live example to render on, and doesn't cover the more common failure type.** The button code is correct, but it requires `payload.id`, which only exists on `INVITE_EMAIL_FAILED` events published after this session's fix — every existing notification in the dev database predates it, so 0 of 4 real failure rows currently show the button (expected, already documented as a graceful-fallback case). Separately, `INVITE_EXPIRED` (7 rows in the current data, more common than email failures) was never given an `id` at all (`sweep-lapsed-invites.use-case.ts`), so it structurally can never get a resend action even going forward. **Fix:** add `id` to the `INVITE_EXPIRED` payload the same way, and reuse the same button.

**[P3] The anonymous médico's own nav permanently advertises "Administração" (the manager panel).** For the one persona whose entire value proposition is employer-blind anonymity, a standing link to the manager dashboard in their own sidebar/sheet is an odd signal — and tapping it dead-ends at a login they have no credentials for. This is worth a product conversation rather than a unilateral fix, since some médicos may also hold a manager role in practice.
